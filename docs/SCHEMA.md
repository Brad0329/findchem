# FindChem 데이터 모델 — 스키마 변경 결정 기록

> **AI는 임의로 컬럼 추가/변경, 마이그레이션 수정을 하지 않는다.**
> 스키마 변경 절차: ① 변경안을 이 문서 '변경 이력'에 먼저 기록 → ② 사용자 확인 → ③ 모델/마이그레이션 반영
> → ④ **구버전 저장본을 실제로 읽어 마이그레이션 실측 + 되돌리기 경로(백업·롤백) 확인 + 사용자 실테스트**
> 후 배포 (일반 트랙 검증 갈래, CLAUDE.md '검증 강도'). 새 코드로 만든 빈 DB는 통과하고 옛 DB만 깨진다.
> 컬럼 목록 등 상세 명세는 손으로 관리하지 말고 모델에서 자동 생성 권장(`<예: scripts/generate_schema_doc.py>`).
> 이 문서는 "결정과 이유"를, 코드(models/migrations)는 "현재 상태"를 담당한다.

## 설계 원칙
- 데이터는 **읽기 전용 빌드 산출물**이다. 고시 별표 PDF를 파싱해 JSON 파일 하나를 만들고, 앱과 웹에 넣는다.
  사용자 데이터는 없다. 나중에 사용자 데이터(즐겨찾기 등)가 생기면 이 파일에 넣지 않고 별도 저장소에 둔다.
- 셀 값은 **원문 문자열 그대로** 저장한다(`"0.2*"`, `"-"`, `"70% 초과"`). 화면에 보여주기만 하고 계산하지 않으므로
  숫자로 바꾸면 정보만 잃는다.
- 항목의 키는 **(src, no)**, 즉 별표와 연번이다. CAS와 고유번호는 키가 되지 못한다(근거: `work_log/Phase_001.md`).

## 핵심 엔티티와 관계
- `entries[]`: 표의 한 항목. 두 별표의 1,657건을 한 배열에 담는다. 1—N `rows[]`(구분별 규정수량)
- 필드(안):
  - `src`: `"별표2"` | `"별표3"`. 내부 식별자다. 화면에는 "인체·생태 유해성" / "사고대비물질"로 표시한다(REQUIREMENTS 용어)
  - `no`: 연번
  - `uid`: 고유번호. 별표3에는 없어서 null
  - `name`: 원문 물질명 전체
  - `ko`, `en`: 원문 물질명에서 뽑은 국문명·영문명
  - `cas[]`: CAS 번호 배열. 없으면 `[]`
  - `deleted`: 별표2의 `(삭제)` 항목 여부
  - `rows[]`: 구분별 규정수량. `{kind 구분, content 함량기준, min 최하위, low 하위, high 상위}`
- 파일 머리(`source`): 원본 PDF 파일명, PDF 생성일, 추출일. 고시 버전 표시와 갱신 확인에 쓴다.

## 도메인별 설계 결정
### 두 별표 합치기
- **결정**: 두 별표를 물질 단위로 병합하지 않는다. **항목 단위로 한 배열에 나란히 담는다.** 두 별표의 관계
  (일반기준 가: 사고대비물질이면 별표3 우선)는 저장하지 않고, 검색할 때 CAS가 겹치면 계산해서 표시한다.
- **이유**: CAS로 합칠 수가 없다. CAS 없는 묶음 항목이 77건, CAS가 여러 개인 항목이 55건이고, 별표2 안에서
  같은 CAS가 두 행에 나오는 경우가 10건이다. 겹치는 93개 CAS 중 23쌍은 수량도 서로 다르다.
- **버린 대안**: CAS 기준 물질 단위 병합 — 위 이유로 기각.
### 저장 형식
- **결정**: JSON 파일 1개(약 561KB, gzip 88KB). 앱이 시작할 때 메모리에 올려 검색한다.
- **올린 PDF로 만든 원천자료(F-002)**: 앱에 번들한 JSON을 덮어쓰지 않는다. 같은 형식으로 기기 저장소에 따로 둔다
  (Android는 앱 저장소, 웹은 브라우저 저장소). 저장본이 있으면 그것을 쓰고, 없으면 번들본을 쓴다.
  두 PDF를 함께 파싱해서 **저장본 1개를 통째로 교체**한다. 부분 갱신은 없다. **되돌리기는 저장본을 지우는 것**이다.
  이 방식은 사용자 결정(2026-09-11: PDF는 함께 올림, 되돌리기 필요)에서 그대로 따라 나온다.
  - 자리(2026-09-12): Android는 앱 지원 디렉토리의 `findchem_update.json`(임시 파일에 다 쓴 뒤 이름을 바꿔 반쯤 덮이지
    않게), 웹은 localStorage 키 `findchem_update`. 코드: `lib/data/update_store*.dart`
  - 필드 뜻: 번들과 같은 형식이다. 저장본에서는 `extractedAt`이 **적용 시각**(설정 화면의 '적용한 날짜'),
    `source.*.file`이 사용자가 고른 파일 이름이다. 새 필드는 없다
- **버린 대안**: SQLite 번들 — Flutter 웹에서는 wasm 설정이 더 필요한데, 1,657건은 메모리 검색으로 충분하다.
  서버 DB — 읽기 전용 데이터라 둘 이유가 없다(plan.md 확정).

### 자주보는 Chem 목록(F-005) — 확정 2026-09-13
> **이 프로젝트의 첫 사용자 데이터다.** 위 '설계 원칙'이 미리 정해 둔 대로("사용자 데이터가 생기면 이 파일에
> 넣지 않고 별도 저장소에 둔다") 번들 JSON·F-002 저장본과 **완전히 다른 파일**에 둔다.

- **결정: 참조가 아니라 스냅샷이다.** 저장 항목마다 **카드를 그리는 데 필요한 것을 전부** 담는다.
  ```json
  { "version": 1,
    "items": [
      { "priority": false, "referenceNote": true,
        "pdfCreated": "2026-07-20T09:16:24+09:00",
        "entry": { "src":"별표2","no":510,"uid":"97-1-345",
                   "name":"포르말린; 포름알데히드 [Formalin; Formaldehyde]",
                   "ko":"포르말린; 포름알데히드","en":"Formalin; Formaldehyde",
                   "cas":["50-00-0"],"deleted":false,
                   "rows":[{"kind":"급성","content":"1","min":"0.05","low":"2","high":"400"},
                           {"kind":"만성","content":"0.1","min":"0.125","low":"5","high":"400"}] } }
    ] }
  ```
  - `entry` = 번들 JSON의 항목과 **같은 형식 그대로**. 파서/모델의 직렬화를 재사용한다(형식을 두 벌 만들지 않는다).
  - `priority`·`referenceNote` = 카드의 '사고대비물질 · 우선 적용' 뱃지와 참고 문구 여부. 이 둘은 **전체
    데이터셋에서 CAS 겹침으로 계산**되는 값이라(`lib/search/search.dart`) 항목만으로는 다시 구할 수 없다. 그래서 함께 담는다.
  - `pdfCreated` = 그 항목이 속한 표 PDF의 생성일. 공유 텍스트 마지막 줄에 쓰고, 목록의 갱신 알림 줄에서
    현재 데이터셋의 기준일과 **문자열 하나로** 비교한다(항목별 대조는 하지 않는다).
  - `version` = 형식 버전. **누적되는 사용자 저장소라 처음부터 넣는다** — 나중에 필드를 늘릴 때 구버전 파일을
    읽는 분기가 필요한데, 버전이 없으면 그 분기를 파일 모양 추측으로 짜야 한다(CLAUDE.md '누적되는 저장소의
    스키마 변경에는 마이그레이션을 같은 커밋에'). YAGNI 예외로 두는 유일한 필드다.
- **왜 참조를 버렸나 (실측 2026-09-13, `scripts/oracle_key_candidates.py`)**: 이 데이터에는 **물질을 가리키는
  안정적인 키가 없다.** 번들 1,657건 전수 측정:
  - `no`(연번)은 그 판 문서의 줄 번호다 — 개정되면 밀린다(사용자 지적). 두 별표를 합치면 100조가 겹친다.
  - `uid`(고유번호) 단독 → 63조 368건 중복(`97-1-9` 하나에 21개 항목). **별표3은 100건 전부 `null`.**
  - `cas` 단독 → 92조 261건 중복. **CAS가 없는 항목이 77건.**
  - `uid+cas` → 아직 11조 25건 중복. 반례: `97-1-9`+`7439-92-1`이 '납(입자지름≥1mm)'과 '납(입자지름<1mm)'
    둘을 가리킨다(규정수량이 서로 다르다).
  - `src+uid+cas+ko` → 1657/1657 유일. 그러나 **이건 지금 한 판을 잰 것**이고 개정 뒤 유지되는지는 알 수 없다.
  → 참조 방식은 매칭이 실패하는 순간 **아무것도 못 보여준다.** 스냅샷은 실패해도 저장할 때 본 내용이 남는다.
    기능을 매칭 성공에 걸지 않는 쪽을 택했다.
- **개정 반영**: 감시하지 않는다. 목록의 **[update] 버튼**(과 F-002 적용 직후의 1회 질문)이 저장 항목을
  현재 데이터셋에서 찾아 스냅샷을 통째로 새로 쓴다. 찾는 규칙과 못 찾았을 때의 처리는 REQUIREMENTS F-005에 있다.
  **못 찾은 항목은 덮지 않는다** — 잘못 맞춰 사용자 저장을 망가뜨리는 것보다 옛 내용이 남는 편이 낫다.
- **자리**: Android는 앱 지원 디렉토리의 `findchem_favorites.json`(F-002 선례대로 임시 파일에 다 쓴 뒤 이름을 바꿔
  반쯤 덮이지 않게). **웹에는 저장소를 두지 않는다** — F-005는 앱 전용이라(사용자 결정 2026-09-12) 웹 구현은
  항상 빈 목록을 돌려주고 저장을 받지 않는다.
- **F-002와의 관계**: 파일이 완전히 별개라 '처음 데이터로 되돌리기'(F-002 저장본 삭제)가 이 파일을 건드리지 않는다.
  거꾸로 저장 목록을 지워도 원천자료는 그대로다.
- **깨진 파일**: 빈 목록으로 조용히 대체하지 않고 사유를 보이고 로그에 남긴다. 자동 삭제하지 않는다(F-002 선례).
- **넣지 않은 필드**: `savedAt`(저장 시각) — 정렬이 가나다 순이라 **쓰이는 곳이 없다**(YAGNI).
  다만 지나간 시각은 나중에 복원할 수 없어서 되돌리기가 한쪽으로만 비싼 선택이다. 넣기로 하면
  `items[]`에 한 줄 더하고 `version`은 그대로 두면 된다(읽는 쪽이 없는 필드를 견디므로).
- **버린 대안**: ① 참조 저장(`src`+`no` 또는 `src`+`uid`+`cas`+`ko`) — 위 실측대로 안정적인 키가 없다.
  ② 이름을 해시해 키로 — 해시는 "같다/다르다"만 답해 부분 일치를 못 한다. 띄어쓰기 하나에 전부 깨지고,
  정규화를 앞에 붙여도 예상한 변화만 흡수한다(사용자 지적 2026-09-13).
  ③ 번들 JSON에 안정적인 `key` 필드를 파서가 만들어 넣기 — 번들 형식 변경(일반 트랙)인데, 스냅샷으로 가면 필요가 없다.
  ④ F-002 저장본에 함께 담기 — 되돌리기 한 번에 사용자 저장이 통째로 날아간다.
