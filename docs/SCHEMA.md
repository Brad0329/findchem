# FindChem 데이터 모델 — 스키마 변경 결정 기록

> **AI는 임의로 컬럼 추가/변경, 마이그레이션 수정을 하지 않는다.**
> 스키마 변경 절차: ① 변경안을 이 문서 '변경 이력'에 먼저 기록 → ② 사용자 확인 → ③ 모델/마이그레이션 반영
> → ④ **구버전 저장본을 실제로 읽어 마이그레이션 실측 + 되돌리기 경로(백업·롤백) 확인 + 사용자 실테스트**
> 후 배포 (일반 트랙 검증 갈래, CLAUDE.md '검증 강도'). 새 코드로 만든 빈 DB는 통과하고 옛 DB만 깨진다.
> 컬럼 목록 등 상세 명세는 손으로 관리하지 말고 모델에서 자동 생성 권장(`<예: scripts/generate_schema_doc.py>`).
> 이 문서는 "결정과 이유"를, 코드(models/migrations)는 "현재 상태"를 담당한다.

## 설계 원칙
- 데이터는 **읽기 전용 빌드 산출물**이다. 고시 별표 PDF를 파싱해 JSON 파일 하나를 만들고, 앱과 웹에 넣는다.
  사용자 데이터는 없다. 나중에 사용자 데이터(즐겨찾기 등)가 생기면 이 파일에 넣지 않고 별도 저장소에 둔다.
- 셀 값은 **원문 문자열 그대로** 저장한다(`"0.2*"`, `"-"`, `"70% 초과"`). 화면에 보여주기만 하고 계산하지 않으므로
  숫자로 바꾸면 정보만 잃는다.
- 항목의 키는 **(src, no)**, 즉 별표와 연번이다. CAS와 고유번호는 키가 되지 못한다(근거: `work_log/Phase_001.md`).

## 핵심 엔티티와 관계
- `entries[]`: 표의 한 항목. 두 별표의 1,657건을 한 배열에 담는다. 1—N `rows[]`(구분별 규정수량)
- 필드(안):
  - `src`: `"별표2"` | `"별표3"`. 내부 식별자다. 화면에는 "인체·생태 유해성" / "사고대비물질"로 표시한다(REQUIREMENTS 용어)
  - `no`: 연번
  - `uid`: 고유번호. 별표3에는 없어서 null
  - `name`: 원문 물질명 전체
  - `ko`, `en`: 원문 물질명에서 뽑은 국문명·영문명
  - `cas[]`: CAS 번호 배열. 없으면 `[]`
  - `deleted`: 별표2의 `(삭제)` 항목 여부
  - `rows[]`: 구분별 규정수량. `{kind 구분, content 함량기준, min 최하위, low 하위, high 상위}`
- 파일 머리(`source`): 원본 PDF 파일명, PDF 생성일, 추출일. 고시 버전 표시와 갱신 확인에 쓴다.

## 도메인별 설계 결정
### 두 별표 합치기
- **결정**: 두 별표를 물질 단위로 병합하지 않는다. **항목 단위로 한 배열에 나란히 담는다.** 두 별표의 관계
  (일반기준 가: 사고대비물질이면 별표3 우선)는 저장하지 않고, 검색할 때 CAS가 겹치면 계산해서 표시한다.
- **이유**: CAS로 합칠 수가 없다. CAS 없는 묶음 항목이 77건, CAS가 여러 개인 항목이 55건이고, 별표2 안에서
  같은 CAS가 두 행에 나오는 경우가 10건이다. 겹치는 93개 CAS 중 23쌍은 수량도 서로 다르다.
- **버린 대안**: CAS 기준 물질 단위 병합 — 위 이유로 기각.
### 저장 형식
- **결정**: JSON 파일 1개(약 561KB, gzip 88KB). 앱이 시작할 때 메모리에 올려 검색한다.
- **올린 PDF로 만든 원천자료(F-002)**: 앱에 번들한 JSON을 덮어쓰지 않는다. 같은 형식으로 기기 저장소에 따로 둔다
  (Android는 앱 저장소, 웹은 브라우저 저장소). 저장본이 있으면 그것을 쓰고, 없으면 번들본을 쓴다. 세부 형식은
  F-002의 미결 질문에 답을 받은 뒤 변경 이력에 기록한다.
- **버린 대안**: SQLite 번들 — Flutter 웹에서는 wasm 설정이 더 필요한데, 1,657건은 메모리 검색으로 충분하다.
  서버 DB — 읽기 전용 데이터라 둘 이유가 없다(plan.md 확정).
